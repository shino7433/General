# スプシ期限リマインダー（LINE / Slack 通知）設計書

- 作成日: 2026-07-13
- プロダクト名（仮）: **スプシ期限リマインダー** ／ 正式名はBOOTH出品時に確定
- 位置づけ: 副業計画（[side-income-goal]）の「売れるGAS資産1本」。同一資産を **BOOTH販売＝ココナラ看板＝CWポートフォリオ第1号** の3チャネルに使い回す。目的は**実績（レビュー）の高速獲得**。

## 1. 目的とコンセプト

スプレッドシートに入力した「期限つきの用事」（請求・支払・入金・契約更新・タスク等）を、期限が近づいたら **LINE / Slack に自動通知**する GAS ツール。買い手は**公開テンプレをコピー → 設定シートに数セル入力 → メニューから初期化＆トリガー設置**で完了する、ノーコード・自己完結型。

受信者は主に**事業主本人／スタッフ向けの自分宛期限通知**を想定（メールは埋もれるため、四六時中見るLINE/Slackに出す）。ターゲットは個人事業主・小規模業者。

## 2. プロダクトの形（買い手体験）

コピー用スプレッドシート（バインドGAS付き）＋日本語手順書。3シート構成:

| シート | 役割 | 主な列/項目 |
|---|---|---|
| **リマインド一覧** | データ入力 | 期限日 / 件名 / 本文 / 有効(TRUE/FALSE) / ＜自動＞送信状態 / ＜自動＞最終送信日時 / メモ |
| **設定** | ノーコード設定 | 通知先(LINE/Slack) / Slack Webhook URL / LINE チャネルアクセストークン / LINE 宛先userId / 送信オフセット(例`7,1,0`) / 超過アラート(ON/OFF) / 1回の送信上限 / 実行時刻 / 差出人名(任意) |
| **送信ログ** | 自動追記 | 日時 / 対象行 / オフセット / 通知先 / 結果 |

- 本文は `{期限日}`『{件名}』`{残り日数}` 等のプレースホルダ差し込みに対応。
- **`初回セットアップ` ワンクリックメニュー**: コピー後にユーザーが押す操作を1つに集約（権限承認 → `setup()` → トリガー設置 → テスト通知1回 まで自動実行）。「動いた」を即体感でき、初期不安を消す（設定摩擦の最小化＝最大の差別化。§7参照）。
- `テスト送信` メニューでいつでも自分宛にプレビュー送信できる。

## 3. アーキテクチャ

GASは全ファイルがグローバルスコープを共有する前提で、CWパイプラインと同じ「純粋関数を分離してNodeでTDD」方式を踏襲する。

```
tools/reminder-mailer/
  core.js       … 純粋関数（Nodeでテスト可能）
  main.js       … GAS結合部（トリガー・UrlFetchApp送信・シート読み書き）
  core.test.js  … node --test
  README.md     … リポジトリ内の開発メモ
  手順書.md      … 買い手向け日本語セットアップガイドの原本
```

### 通知アダプタ（差し替え式）
コア（期限計算・オフセット・冪等な送信状態管理）は**通知先に依存しない**。メッセージ生成後、通知先で分岐:

```
リマインドコア（純粋）
  → renderTemplate(件名/本文, 変数) でメッセージ生成
  → notify(通知先, 設定, メッセージ)
       ├─ Slack: buildSlackPayload() → Webhook URL に UrlFetchApp POST
       └─ LINE : buildLinePayload()  → Messaging API push（userId宛）
```

- **Slack**: Incoming Webhook。設定にURLを1本貼るだけ。送信数上限なし・最も確実。
- **LINE**: **LINE Notify は 2025-03 終了済みのため Messaging API push を使う**（公式アカウント＋チャネル＋アクセストークン＋userId）。無料枠は月200通程度＝設定シートと手順書で明示。
- v1では **Gmail アダプタは載せない**（受信層をLINE/Slackに寄せる方針）。将来アダプタ追加は容易。

### core.js に置く純粋関数（テスト対象）
- `parseOffsets(str)` → `"7,1,0"` を `[7,1,0]` に。不正値は除外。
- `daysUntilDue(today, dueDate)` → 期限までの日数（負なら超過）。
- `selectDue(rows, today, config)` → 送信すべき `{row, offsetLabel, 件名, 本文}` の配列。オフセット一致かつ未送信のものだけ。超過はconfig次第。
- `renderTemplate(text, vars)` → プレースホルダ差し込み。
- `parseSentState(cell)` / `markSentState(cell, offsetLabel)` → 送信済みオフセットの解析・追記（冪等の要）。
- `buildSlackPayload(message, config)` / `buildLinePayload(message, config)` → 各APIのリクエストボディ生成。

### main.js（GAS結合部・テスト対象外）
- `onTimeTrigger()` … 設定/一覧を読み、`selectDue` → `notify` → 送信状態・最終送信日時・ログを書き戻し。送信上限を尊重。
- `installDailyTrigger()` … 設定の実行時刻で日次トリガー設置。
- `sendTestNotification()` … 自分宛プレビュー送信（1件）。
- `setup()` … シート/ヘッダ/データ検証が無ければ生成（テンプレの堅牢化）。

## 4. 発火ロジック（1回の実行 = 日次）

1. `today` = トリガー実行日。設定を読む（オフセット・超過・上限・通知先）。
2. 「リマインド一覧」の各行（有効=TRUEかつ期限日が有効な日付）について:
   - `d = daysUntilDue(today, 期限日)`
   - 設定オフセット `N ∈ [7,1,0]` で、`d == N` かつ 送信状態に `-N` が未記録 → その行の通知を送信予定に。ラベルは `-N`（当日は `0`）。
   - 超過（`d < 0`）: 超過アラートONなら、送信状態に `超過` が未記録のとき1回だけ送信予定に（v1は超過通知は**1回のみ**。毎日催促はしない＝スパム回避と冪等の単純化）。
3. 送信予定を上限まで送信。各送信ごとに `notify()` を呼び、成功したら送信状態へラベル追記＋最終送信日時更新＋ログ追記。
4. **冪等性**: 同日に再実行しても、送信状態に記録済みのオフセットは再送しない。

## 5. エラー処理・安全弁

- 不正な期限日 / 空の宛先設定 → その行/送信をスキップし、ログに理由を残す。
- **行単位 try-catch**: 1件の失敗が全体を止めない。
- **1回の送信上限**（設定値）: LINE無料枠（月200通目安）・Slack/APIレート・暴発を防ぐ。
- LINE Messaging API のエラー（トークン失効・userId不正・quota超過）はログに記録し、その回は打ち切り。
- 通知先未設定（Webhook URL / トークン空）→ 送信せず設定不備を明示。

## 6. テスト方針（TDD）

CWパイプラインと同流儀。`core.js` の純粋関数を `node --test` で先にテスト（RED→GREEN）。最低限のケース:
- `parseOffsets`: 正常/空白混じり/不正値除去/空入力。
- `daysUntilDue`: 未来/当日/超過、月またぎ。
- `selectDue`: オフセット一致で選定 / 未送信のみ / 送信済みは除外 / 超過ON・OFF / 無効行スキップ。
- `renderTemplate`: 各プレースホルダ差し込み / 未知プレースホルダは素通し。
- `parseSentState`/`markSentState`: 追記の冪等・重複防止。
- `buildSlackPayload`/`buildLinePayload`: 期待JSON形状。

GAS結合部（`main.js`）は単体テスト対象外。`sendTestNotification()` と手動実行で結合確認。

### 調査からの2つの事実
1. **機能の新規性では差別化できない**: 「期限前リマインド＋LINE/Slack＋スプシ」は gasoji ¥2,980 が既にほぼ同一で提供済み。
2. **BOOTHは購入者レビューがほぼ非表示**（gasojiページにもレビュー欄なし）＝「不満コメントで差別化」の一次データはBOOTHから取れない。**不満データはレビューが厚いココナラ側**にある。ただし市場は既に不満を価格で暴露している: OwnerOSが「動くまで一緒にいます・セットアップ完了保証」を **+¥15,000**（¥14,800→¥29,800）で販売＝**このカテゴリ最大の不満は「買ったのに自力で設定できない/動かない」**。

### 差別化＝「価格 vs 不満点」は二者択一でなくチャネルで層別
価格の底なし競争（¥2,980→¥1,480→¥100）は不毛。勝ち筋は**「設定できない」という最大の不満を潰す**こと。本設計は既にそこを突ける:
- **信頼性**: 冪等な二重送信防止（競合は明示していない）。
- **設定ゼロ摩擦**: 設定シートだけ＋`テスト送信`で"動いた"を即体感。
- **LINE Notify終了に完全対応**した最新Messaging API手順（古いツール/教材はNotify前提が残存＝地雷。ここを明記が刺さる）。
- **つまずき0の日本語手順書**。

**チャネル別の役割（価格戦略）**:
1. **BOOTH＝価格を入口ウェッジ**: ¥980〜1,480（gasoji¥2,980より下・捨て値より上）で**レビュー実績を高速獲得**。
2. **ココナラ＝不満(設定)を価値ウェッジ**: 「セットアップ代行・動作保証」付きを中価格 ¥3,000〜8,000 で。OwnerOSが実証した"設定サポートに金を払う層"を取る。

### 実装原則: セットアップ最小化と手順書（本プロダクトの中核差別化）
最大の不満「設定できない/動かない」を潰すことが勝ち筋なので、以下を**機能要件と同格の必須要件**として扱う。

**A. エンドユーザーの手順を極小化する**
- **操作数を数える**: コピー後にユーザーが行う操作を最小に。目標＝**Slack: 3ステップ以内（①テンプレをコピー ②Webhook URLを1つ貼る ③`初回セットアップ`を押す）**。LINEは項目が多いぶん、貼る欄を最小化し手順書で完全ガイド。
- **ワンクリック集約**: 権限承認・`setup()`・トリガー設置・テスト通知を `初回セットアップ` 1操作にまとめる（§2）。ユーザーにコードやトリガー画面を触らせない。
- **既定値を埋めて配布**: オフセット`7,1,0`・サンプル行・記入例をテンプレに同梱。空欄を最小化し「何を入れるか」を迷わせない。
- **親切な検証**: 必須項目（通知先・Webhook/トークン）が空なら、`初回セットアップ`／`テスト送信`が**何が足りないかを日本語で明示**して止まる（黙って失敗しない）。
- **LINEの難所を軽減**: OA作成・トークン・userId取得は手順書で1クリックずつ図解。userId取得を補助する手段（例: 一時的な取得ヘルパー or LINE Developers画面の図解）を用意し、詰まりどころを消す。

**B. 手順書は画面キャプチャ多用でわかりやすさ最優先**
- **1ステップ＝1スクショ**を原則に、実際の画面キャプチャを多用。赤枠・矢印・連番の注釈を必ず入れる。
- **通知先ごとに手順を分岐**（Slack編／LINE編）。混在させない。
- **ゴール画像を先に見せる**（テスト通知が届いた画面）→ 到達点を明確化。
- **つまずきポイントFAQ**（権限承認で警告が出る／通知が来ない／LINEのトークン失効／月200通の壁 等）と各ステップの**所要時間目安**を併記。
- スクショは実装時に実際のSheets/Slack/LINE画面を操作して取得する（ブラウザ操作で撮る）。手順書は `手順書.md` を原本に、配布はPDF化。

### 未確定・次アクション
- ココナラのレビュー不満点の一次データ採取は、**別サブプロジェクト「ココナラ立ち上げ」で実施**（BOOTHに無いため）。得られた具体的不満で手順書/FAQ/出品文を補強する。

## 9. スコープ（v1のYAGNI）
**やる**: 期限オフセット＋当日＋超過 / LINE＋Slack両対応 / 冪等な送信状態 / 設定シート / `初回セットアップ`ワンクリック / テスト送信 / 送信ログ / プレースホルダ差し込み / 送信上限 / **スクショ多用の日本語手順書（Slack編・LINE編）＋つまずきFAQ**。

## 11. 成功基準
- テンプレをコピーした第三者が、手順書だけで **LINE または Slack にテスト通知を出せる**（設定〜稼働まで詰まらない）。**Slackは3ステップ以内**で到達。
- 手順書が**1ステップ＝1スクショ**で、通知先別（Slack編/LINE編）＋つまずきFAQを備え、コードやトリガー画面をユーザーに触らせない。
- コア純粋関数のテストが全緑で、冪等（再実行で二重送信ゼロ）を自動テストで保証。
- BOOTH公開後、**最初のレビュー獲得**（実績第1号）。
