# 設計: CW案件パイプライン フェーズ2「Claude評価ループ」

- 日付: 2026-07-07
- ステータス: 設計承認済み（実装プラン作成へ）
- 前提: フェーズ1（GAS収集→GSS）は稼働中。[2026-07-07-cw-案件パイプライン-design.md](2026-07-07-cw-案件パイプライン-design.md) の③にあたる部分を具体化する。
- 関連: [crowdworks.md](../../crowdworks.md)（獲得プレイブック＝判定基準の正）、[freelance.md](../../freelance.md)（提案テンプレ）、[proposals/](../../proposals/)（提案ワークフロー）

## 1. 目的・背景

稼働中の「案件管理」シートには、GASがCWメールから収集した案件が `未判定` で溜まっていく。この未判定案件を、ローカルのログイン済みChromeを使って自動評価し、Go/No-Go・見積・提案文ドラフトまで用意して、仕事終わりに（出先からも）レビューできる状態にする。**送信は必ず人間が行う。**

CWの案件ページはログイン外から取得できない（クラウド側Claudeは crowdworks.jp が遮断）。唯一の一次情報源は**ローカルのログイン済みブラウザ**であり、これがフェーズ2をローカル実行に固定する根拠。

## 2. 全体アーキテクチャ

2つのランタイムを、GAS Web App API 1点で接続する。

```
[毎日18時ごろ・ローカル]
  scheduler ──起動──▶ Claude評価ループ(エージェント手順/runbook)
                          │  ① curl GET ?token&view=pending
                          │◀──────────────▶ ┌────────────────────┐
                          │                  │  GAS Web App        │
        ② claude-in-chrome│                  │ (既存プロジェクト拡張)│
           で案件ページ閲覧 │                  │  doGet / doPost      │
        ③ 判定・見積・ドラフト│                 │  + HTMLダッシュボード │
                          │  ④ curl POST      └─────────┬──────────┘
                          │     {jobId,eval}            │ 読み書き
                          │                       ┌─────▼─────┐
        ⑤ proposals/保存    ▼                      │ GSS「案件管理」│
           + git push                             │ E/F/G, J〜R  │
                                                 └────────────┘
   [出先] スマホで ?view=summary&token=XXX を開いて確認
```

| 部品 | 責務 | 種別 |
|---|---|---|
| GAS Web App（既存拡張） | シートの入出力・ダッシュボード配信。壊れやすいUI操作を排除 | **決定的コード**（テスト対象） |
| ローカル評価ループ | 案件ページ読取・Go/No-Go判断・提案文ドラフト | **Claudeのエージェント手順**（LLM判断） |

**知能と決定的コードの線引き**（重要）:
- **Claudeが担う（非決定的）**: 案件ページの読み取り、Go/No-Go判定、見積の妥当性判断、提案文ドラフト生成。判定基準は [crowdworks.md](../../crowdworks.md) §2/§4/§5/§7 ＋ [freelance.md](../../freelance.md) §4 をコンテキストに入れて適用する。
- **決定的コード（テスト対象）**: 見積レンジの算出、pendingフィルタ、案件ID→行の引き当て、トークン照合、eval→列マッピング。フェーズ1と同じTDD方針（`node --test`）。

## 3. 起動モデル

- 日次でローカル起動（目安18時）。仕事終わりに、その日の未判定をまとめて評価しレビュー可能にする。
- **前提**: 起動時刻にMacが稼働し、Chromeが CW/Google にログイン済みであること。CWがクラウド遮断のため必ずローカル実行。
- **未確定（実装プランで確定）**: 起動方式。候補＝`/loop`の日次ペーシング／手動トリガー（「未判定を評価して」）／macOS launchd。cron等でheadless起動すると claude-in-chrome 拡張が繋がらない可能性があるため、Chromeセッションが生きた状態で回せる方式を選ぶ。Macがオフの日は次回起動時にまとめて処理（pendingゲートにより取りこぼさない）。

## 4. GAS Web App 仕様

既存「CW案件パイプライン」プロジェクトに `api.gs`（＋ダッシュボードHTML）を追加。

### 4.1 デプロイ・認証
- デプロイ: ウェブアプリ、「次のユーザーとして実行: 自分」「アクセス: 全員（匿名）」。
- 認証: 秘密トークンを `PropertiesService.getScriptProperties()` に保存し、全リクエストで照合。URLに `?token=XXX` を付与。トークン不一致は403。
- 匿名公開だが、トークンなしでは何も返さない。露出範囲はこのエンドポイントの機能に限定され、Googleアカウント全体ではない。

### 4.2 エンドポイント

| メソッド | パラメータ | 動作 | 返り値 |
|---|---|---|---|
| GET | `?token&view=pending` | 列J＝`未判定`の行を返す | `[{jobId,url,title,sourceType,row}]`（JSON） |
| GET | `?token&view=summary` | 評価済み案件のダッシュボード | HTML |
| POST | `{token,jobId,eval:{...}}` | 案件ID（列A）で行を引き、E/F/G・J〜R を書き戻し | `{ok:true,updatedRow}` |

- `doPost` は案件IDで行検索するため行番号ズレに強い。案件IDが無ければ404。
- `eval` の想定キー: `カテゴリ,予算,報酬形態,判定,判定理由,提案数,見積,想定実稼働,提案ドラフト`（＋失敗時 `結果メモ`）。

### 4.3 ダッシュボード（`view=summary`）
- 直近の評価済み行を、Go/NoGoバッジ・タイトル・提案数・見積・想定実稼働・判定理由で一覧表示。
- Go案件は提案ドラフト本文を展開表示（インライン）。案件URLへのリンクも付ける。
- スマホから `?view=summary&token=XXX` をブックマークして出先で確認。

## 5. 列のセマンティクス（フェーズ1の枠を活用し確定）

| 列 | ヘッダー | 誰が/いつ | 意味 |
|---|---|---|---|
| E/F/G | カテゴリ/予算/報酬形態 | 評価ループ | フェーズ1で空にしていた欄。案件ページから補完 |
| J | ステータス | ループ→人 | ワークフローの現在地。ループが `未判定 → Go/NoGo` に進める（＝pendingゲート）。以降は人が `応募済→受注…` |
| K | 判定 | ループ | 評価時のGo/No-Go verdict を凍結記録（Jが後で応募済等に進んでも残る） |
| L | 判定理由 | ループ | Go/No-Goの根拠 |
| M | 提案数 | ループ | 評価時点の提案数 |
| N | 見積 | ループ | §5段階＋§7単価表から算出 |
| O | 想定実稼働 | ループ | 基準2〜4h |
| P | 提案ドラフト | ループ(Go時) | **ドラフト本文**（ダッシュボードにインライン表示）。正本は `proposals/` にも保存しGitHub push |
| Q | 応募日 | 人 | 送信後に記入 |
| R | 結果メモ | 人/ループ | 通常は人。ループは失敗時のエラーメモに使う場合あり |

## 6. ローカル評価ループ手順（runbook）

日次起動でClaudeが以下を実行。1案件ずつ、人間ペース（案件間に小休止）。

1. `curl GET ?view=pending` で未判定行を取得（0件なら即終了）。
2. 各案件について:
   1. claude-in-chrome で `url`（案件ページ）を**閲覧のみ**で開き、提案数・クライアント評価・予算・報酬形態・カテゴリ・要件全文・「継続/長期」有無・悪質シグナルを取得。
   2. **Go/No-Go判定**（[crowdworks.md](../../crowdworks.md)基準）:
      - **No-Go**: 提案数30件超／時間単価制・コンペ形式／月数十時間の常駐（週10h制約違反）／未経験優先・カンタン作業・情報商材シグナル(§7)／直接取引誘導／クライアント評価4.5未満・仮払いを渋る。
      - **Go**: 固定報酬・提案数少なめ（理想は5件未満）・要件具体・定番4型/AI系に合致。
   3. **見積・想定実稼働**: §5段階（評価0〜2件は下限5,000〜10,000円の小型中心）＋§7単価表、想定実稼働2〜4hを基準に算出。
   4. **Go案件のみ提案ドラフト生成**: 型A（要件明確）/型B（曖昧＝ヒアリングで質問終わり）を [crowdworks.md](../../crowdworks.md) §4 ＋ [freelance.md](../../freelance.md) §5 テンプレで。型Cデモは対象外。
3. `curl POST {jobId, eval}` でE/F/G・J・K〜P を書き戻し（J＝Go/NoGo、Go案件はP＝ドラフト本文）。
4. Go案件のドラフト正本を `proposals/YYYY-MM-DD-案件.md`（`_template.md`使用）に保存。
5. 全案件処理後、`proposals/`＋progressをまとめて日本語コミット＆push。ダッシュボードは即反映。

## 7. エラー処理

1件の失敗で全体を止めない。各案件は独立処理（try/catch相当）。

- 案件が404/募集終了 → `J=クローズ`＋`R`にメモ（次回再処理しない）。
- ページ解析失敗（DOM変化・読み取り不能）→ `J=未判定`のまま＋`R`にエラーメモ → 次回再試行。連続失敗はダッシュボードで要調査として可視化。
- `curl`失敗 → 数回リトライ。トークン不正なら明確なメッセージで中断。

## 8. ガードレール（規約・安全）

- ループは案件ページを**閲覧するだけ**、書き込み先は**自分のシート/リポジトリのみ**。CW上の応募・送信・メッセージは**絶対に押さない**（送信は必ず人）。
- 人間ペース（案件間に小休止・1日の未判定は通常一桁）。多重・高速アクセスをしない。
- §7の悪質/情報商材シグナルは自動No-Go。仮払い・契約操作はスコープ外。
- APIは自分のシート/リポジトリのみを対象。トークンは秘匿。

## 9. テスト・受入基準

**テスト**
- 決定的な純粋関数（見積算出、pendingフィルタ、案件ID行引き、トークン照合、eval→列マッピング）→ `node --test`。
- 案件ページ解析ヘルパ → 保存した実ページのテキスト断片をフィクスチャにしてテスト（生ページ依存を排除）。
- GAS `doGet/doPost` → Apps Scriptエディタ＋`curl`スモークテストで手動検証。
- ダッシュボードHTML → 目視。

**受入基準（MVP）**
1. `view=pending` が未判定行のみを正しくJSONで返す。
2. ループ実行で、各未判定案件が評価され、E/F/G・J・K〜O（Goなら＋P）が書き戻される。
3. 再実行で評価済み行が再処理されない（Jゲートで冪等）。
4. Go案件の提案ドラフトが `proposals/` に保存されGitHub pushされる。
5. `view=summary` ダッシュボードがスマホから開け、Go/NoGo・見積・ドラフト本文が確認できる。
6. CW上で応募・送信を一切行わない（閲覧＋自分のシート/リポジトリ書き込みのみ）。

## 11. スコープ境界（YAGNI）

- **対象**: 判定＋見積＋型A/B提案ドラフト＋書き戻し＋ダッシュボード。
- **非対象（後続フェーズ）**: 型Cデモ自動生成、応募後のステータス運用（応募済→受注→納品）、月次KPI自動集計、起動方式の最終確定（実装プランで詰める）。

## 12. 未確定事項（実装プランで確定）

- 日次起動方式（`/loop` / 手動 / launchd）と、Chromeセッション生存の担保。
- ダッシュボードの表示範囲（当日のみ / 直近N件 / 未応募Goのみ 等）。
- 案件ページの解析対象セレクタ/文言（実ページを見て確定。壊れにくいテキストベース抽出を優先）。
- 見積算出式の具体（評価数の現在値をどう持つか＝定数 or シート参照）。
