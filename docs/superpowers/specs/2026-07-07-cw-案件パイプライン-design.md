# 設計: CW案件パイプライン（GAS × スプレッドシート × Claude）

- 日付: 2026-07-07
- ステータス: MVP（フェーズ1）を実装対象として承認済み
- 関連: [crowdworks.md](../../crowdworks.md)（案件獲得プレイブック）、[proposals/](../../proposals/)（Go/No-Goワークフロー）、[cw-profile.md](../../cw-profile.md)

## 1. 目的・背景

CWの良案件は掲載から24時間以内に競合が集中する（[crowdworks.md §2](../../crowdworks.md)）。新着を人が定期的に探すのは負荷が高く取りこぼす。そこで、CWからのメール通知を起点に案件を自動収集し、スプレッドシート（GSS）を案件管理のハブとして、受注〜納品まで一元管理する仕組みを作る。

副次効果: この仕組み自体が当方の売り物（GAS×スプレッドシート自動化）そのものであり、動けばポートフォリオ第1号を兼ねる（[freelance.md §3](../../freelance.md)）。

## 2. 全体アーキテクチャ（最終形）

```
[CW通知メール] → (① GAS/時間トリガー) → [② GSS 案件管理シート] → (③ Claude /loop・ローカル) → 判定・提案・受注管理
  スカウト/おすすめ/    メール解析・重複排除     一元管理ハブ            本格Go/No-Go＋提案ドラフト
  保存検索新着          案件を追記(未判定)
```

| 部品 | 責務 | 実行環境 |
|---|---|---|
| ① GAS収集スクリプト | CWメールから案件を抽出しGSSに追記（重複排除） | ユーザーのGoogleアカウント（時間トリガー） |
| ② GSS 案件管理シート | 全案件の一元管理ハブ（収集＋判定＋提案＋ステータス） | Google スプレッドシート |
| ③ Claude評価ループ | `未判定`行を巡回し、CWページを開いてGo/No-Go＋見積＋提案ドラフト | ローカルChromeセッション（開いている間） |

### 責務の線引き（重要）

- **① GASはメールの範囲だけを扱う**。CWページのスクレイピングはしない（規約・技術両面で回避。ログアウト状態のGASからCW案件ページは取得できない）。
- **CWにアクセスするのは③Claude（ローカル）だけ**。提案数・クライアント評価・要件全文はここで取得する。
- したがってGASが埋められるのは **案件ID・URL・タイトル(件名由来)・ソース種別・取得日時** まで。**予算・カテゴリ・提案数は③で埋める**。

## 3. MVPスコープ（フェーズ1）

**本設計で実装するのは①GAS収集→②GSS追記のみ。** ③Claude評価ループと受注管理の運用はフェーズ2以降。ただし②のシート列は最終形を最初から用意し、後で作り直さない。

MVPの完成定義: GASを時間トリガーで動かすと、CWから届いた新着メール・スカウトメールに含まれる案件が、重複なくGSSの「案件管理」シートに `未判定` で溜まっていく。

## 4. GSS「案件管理」シート設計

1行目をヘッダーとする。列J「ステータス」はデータの入力規則（プルダウン）を設定。

**GASが埋める（MVPの範囲）:**

| 列 | ヘッダー | 内容 | 備考 |
|---|---|---|---|
| A | 案件ID | CWのjob ID（URL末尾の数字） | **重複排除キー**。文字列として保持 |
| B | 取得日時 | GASが追記した日時 | |
| C | 掲載日 | メールにあれば | 通常は空（メールに無い） |
| D | タイトル | 案件タイトル（メール件名由来） | |
| E | カテゴリ | 業務システム等 | 通常は空（③で埋める） |
| F | 予算 | 例:1万〜3万円 | 通常は空（③で埋める） |
| G | 報酬形態 | 固定/時給/タスク | 通常は空（③で埋める） |
| H | URL | 案件ページURL（`public/jobs/<ID>`） | ③が案件ページを開く入口 |
| I | ソース種別 | スカウト / おすすめ / 保存検索 / その他 | 件名・本文から判定 |
| J | ステータス | 既定 `未判定` | プルダウン:未判定/Go/NoGo/応募済/受注/失注/納品/クローズ |

**③Claude評価・手動で埋める（MVPでは空欄で用意だけ）:**

| 列 | ヘッダー |
|---|---|
| K | 判定（Go/No-Go） |
| L | 判定理由 |
| M | 提案数（評価時） |
| N | 見積 |
| O | 想定実稼働 |
| P | 提案ドラフト（repoリンク） |
| Q | 応募日 |
| R | 結果・メモ |

## 5. ① GAS収集スクリプト仕様

### 5.1 トリガー
- 時間主導トリガー: 1時間ごと（頻度は運用で調整可）。

### 5.2 対象メールの取得
- Gmail検索クエリ: 送信元 `no-reply@crowdworks.jp`（必要なら `from:crowdworks.jp`）。
- 前回実行以降の新着のみ処理する。方式: スクリプトプロパティに前回処理済みの最終メール日時（またはGmailスレッドID集合）を保存し、それ以降を対象にする。取りこぼしと二重処理を避ける。

### 5.3 案件の抽出（パース）
- 各メール本文（プレーンテキスト/HTML）から正規表現で **`crowdworks\.jp/public/jobs/(\d+)`** に一致するURLを全て抽出し、案件IDのユニーク集合を得る。
  - 案件URLの形式は全メール種別で共通のため、パーサは1種類で済む。
- タイトル: メール件名から装飾（`【クラウドワークス】` や末尾の定型句「…について相談がありました」等）を除去して採用。件名から取れないメールはタイトル空で可（③で補完）。
- ソース種別（列I）の判定ヒューリスティック:
  - 件名/本文に「相談がありました」「スカウト」等 → `スカウト`
  - 保存検索由来の新着通知の定型文言 → `保存検索`（実物のメールが届いたら文言を確定）
  - CWのおすすめ/レコメンド定型 → `おすすめ`
  - いずれも不明 → `その他`

### 5.4 重複排除と追記
- GSSの列A（案件ID）に既出のIDはスキップ。
- 新規IDのみ、4章の列に沿って行を追記。ステータスは `未判定`、取得日時は実行時刻。
- 同一実行内でも重複IDは1行に集約。

### 5.5 非対象・ガード
- CW案件ページへのアクセス（スクレイピング）はしない。
- 案件URLを含まないメール（認証コード・ログイン通知・純粋な事務連絡等）は無視。
- オンボーディングメール等に紛れる例示URLを拾う可能性はあるが、③Claude評価で除外されるため許容（必要なら既知の非案件IDを除外リスト化）。

## 6. 依存・前提

- ユーザーのGoogleアカウント（`kazu1547bbss@gmail.com`）でGSSとGAS（コンテナバインド or スタンドアロン）を用意する。
- GASにGmail/スプレッドシートのスコープ承認が必要（初回実行時にユーザーが承認）。
- 実物の「保存検索の新着メール」が届いたら、5.3のソース種別判定文言を実データで確定する（MVPは既に届いているスカウト/おすすめメールで動作検証可能）。

## 7. テスト・受入基準（MVP）

1. 手動実行で、既存のCWメール（スカウト等）から案件が正しくGSSに追記される。
2. 再実行しても重複行が増えない（案件IDで冪等）。
3. 案件URLを含まないメール（認証コード等）は追記されない。
4. ソース種別が妥当に分類される（少なくともスカウトを識別）。
5. 時間トリガーで無人実行されても1〜3が保たれる。

## 10. 今後のハードニング（最終レビューで記録・MVPでは非対応）

- **`detectSourceType` の判定順**: 現状「保存検索」パターン（`新着のお仕事` 等）を「おすすめ」より先に評価するため、「あなたにおすすめの新着のお仕事」のような件名が保存検索へ誤分類され得る。実物の おすすめ／保存検索メールが届いたら 5.3 の文言と判定順を確定する。
- **Gmail検索の50スレッド上限**: `collectCwJobs` は `GmailApp.search(query, 0, 50)` で最大50スレッド。検索窓 `newer_than:7d` と組み合わせ、7日級のトリガー停止＋大量受信が重なると古いスレッドが取りこぼされ、チェックポイント前進により恒久スキップになり得る（当ユーザーの受信量では低確率）。受信量が増えたらページング（ループで残りを取得）を検討。
- **`getExistingIds` のループ内再読み込み**: メール1通ごとに列A全体を再読み込みするため、件数が増えるとSheets API呼び出しが増える（現状は実害なし・冪等性は担保）。件数増加時にバッチ化を検討。
